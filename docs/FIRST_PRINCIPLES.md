# 第一性原則開發說明

## 核心問題

本專案不是問「如何做 Tomodachi Life 網頁版」，而是問：

- 為什麼觀察虛擬居民會有趣？
- 居民要具備哪些最小狀態，才會像在生活？
- 玩家介入需要多深，才會覺得自己有影響？
- 哪些故事可以由規則自然產生，而不是全部寫死？
- 如何在不使用受保護 IP 的前提下，做出同類型樂趣？

## 第一性拆解

社交生活模擬的基本材料：

- 主體：居民。
- 狀態：心情、需求、能量、喜好。
- 關係：居民彼此如何看待對方。
- 場所：居民在哪裡活動。
- 事件：狀態與關係碰撞後產生的事情。
- 介入：玩家能做出的選擇。
- 記憶：世界如何記住已發生的事。

只要這些材料能互相影響，就能產生「小世界正在運轉」的感覺。

## 玩家循環

遊戲應先建立這個循環：

1. 玩家看到居民狀態或事件。
2. 玩家選擇是否介入。
3. 系統更新居民心情、需求與關係。
4. 世界記住事件。
5. 新事件因為新的狀態被觸發。

這個循環比大量角色、美術、裝飾或功能更重要。

## MVP 優先順序

1. 居民資料結構能運作。
2. 心情、需求與關係會改變。
3. 事件能依條件產生。
4. 玩家行動能改變事件結果。
5. 狀態能保存到本機。
6. UI 能清楚呈現居民與事件。
7. 再加入更多事件、物品、裝飾與動畫。

## 事件設計原則

事件不應只是隨機文字。每個事件至少需要：

- 觸發條件。
- 參與居民。
- 玩家選項。
- 狀態影響。
- 事件紀錄。

範例：

- 條件：居民 A 心情低，社交需求高。
- 事件：居民 A 想找人聊天。
- 選項：安排居民 B、讓 A 獨處、送小禮物。
- 結果：心情、關係與記憶更新。

## 技術決策原則

這類遊戲的重點在狀態、事件與 UI，不是高強度物理或即時戰鬥。

MVP 建議：

- TypeScript 管理資料與規則。
- Vite 建立前端。
- DOM/CSS 或 Canvas 呈現社區畫面。
- localStorage 或 IndexedDB 儲存進度。
- Vitest 測試事件規則。

先用資料驅動的事件系統做出可擴充骨架，再決定是否需要 Phaser 或其他遊戲框架。

## 反複雜度原則

MVP 先不做：

- 多人連線。
- 帳號系統。
- 付費機制。
- AI 對話生成。
- 複雜紙娃娃系統。
- 3D 場景。
- 大型房屋編輯器。

除非核心玩法已經穩定，否則先不要把內容量和技術複雜度混在一起。
